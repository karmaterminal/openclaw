## Ingress-time vs turn-time

### Per-message ingress before queueing

These decisions run against each source before it reaches follow-up queue aggregation and therefore already cover each aggregate member independently:

- **Channel DM/group allowlists, route policy, pairing, owner/auth checks.** Discord preflight and inbound context pass an admitted sender to group/route/tool policy at `extensions/discord/src/monitor/inbound-context.ts:85-100`; Telegram performs DM/group/sender allowlist authorization at `extensions/telegram/src/bot-handlers.inbound-authorization.ts:208-251` and `:292-318`; Slack authorizes each DM sender at `extensions/slack/src/monitor/dm-auth.ts:10-79`. Other bundled channel plugins have analogous ingress gates in their monitor/bot handlers.
- **`before_channel_ingress`.** Plugin hook can transform/reject channel ingress before queue admission. Its event/context is ingress-owned, not a turn replay surface: `src/plugins/hook-types.ts:129,216-220`.
- **`inbound_claim` and plugin channel bindings.** Admission can be claimed by a plugin or channel binding before turn adoption; contexts include sender where the channel supplies it: `src/plugins/hook-message.types.ts:73-140,181-220`.
- **`message_received`.** It is emitted after accepted inbound context and is fire-and-forget observation by the traced caller, not a queue-admission decision: `src/auto-reply/reply/message-received-hooks.ts:11-40`. It carries canonical sender facts (`from`/`senderId` and metadata) before/around dispatch, not an aggregate turn after queueing.

### Turn-time only (the true aggregate exposure)

- Typed agent hooks and gate hooks: `before_agent_run`, `before_model_resolve`, `before_prompt_build`, `before_agent_reply`, `llm_input`, `llm_output`, finalization/end hooks.
- `before_tool_call` and `after_tool_call`; plugin tool factory execution.
- `message_sending`/`reply_payload_sending`/`message_sent` while delivering an aggregate turn.
- Channel plugin `handleAction`/`requiresTrustedRequesterSender` and group/tool-policy callbacks invoked by the shared tool/message path.
- Plugin runtime tool behavior that reads `requesterSenderId` or `senderIsOwner`.

Ingress allow/deny decisions do **not** prove turn-time plugin behavior: queue admission can collect different accepted members only after each member passed its own ingress gate.

## Whether the plugin consent model has a core-readable signal

**Traced:** the existing manifest activation capabilities are only provider/channel/tool/hook load hints (`src/plugins/manifest-types.ts:172-197`). They do not declare sender authorization, participant authorization, or pure turn-time sender evaluation. Hook registration has `eligibleTriggers`, tool ownership, and `requiresToolAuthority`, but no registration field equivalent to “this plugin makes an allow/deny decision from sender identity”: `src/plugins/hook-types.ts:213-218`.

There is a runtime registration-level capability for tool `contextVersion: 2` owner-authorized continuations (`src/plugins/registry-types.ts:72-77`), but this says when final-effect authority is required, not whether the plugin consumes sender identity as a policy input. Thus core cannot currently infer aggregate safety from manifests or registrations.

## Design options

### (a) Admit a member only if no active plugin consumes sender identity for turn-time authorization

Minimal declaration:

```text
manifest.activation.onCapabilities:
  add "turnTimeSenderAuthorization" or a narrower "turnTimeSenderDecision"

Plugin SDK registration:
  declare "senderAuthorization": true for a hook, tool, channel action, or runtime resolver
```

The declaration should be manifest/load-plan-visible for fail-safe admission, with runtime registration verification that no undeclared implementation is accepted. Hook/tool/channel runtime surfaces need distinct operation kinds only if core must replay or gate them.

- Cost: low core complexity, but the fleet and third-party plugin ecosystem need explicit migration.
- Unknown/unversioned plugins must default to unsafe/blocked.
- This can keep aggregation off whenever any declared active plugin exists, so it is conservative but may disable Discord/active-memory/Codex fleet aggregation even if members share the actual result.

### (b) Pass participant identities to plugin hooks

Suggested shape:

```text
ctx.aggregate = true
ctx.senderId = undefined
ctx.participants = [{ senderId, senderName, roles?, ... }]
```

- Cost: moderate SDK change plus plugin opt-in or migration.
- Safety: this is **not safe by itself for plugins that do not read the new field**. Existing hooks read `ctx.senderId` and will still see absence; plugins using the same allow/deny/fallback shape remain vulnerable unless core also changes or rejects their decision.
- Existing plugins ignore the field and retain behavior, so b needs compatibility-by-harness: old sender-aware plugins must be detected and blocked or evaluated, otherwise the field change creates only an illusion of protection.
- It is not enough to expose participant identities if plugin code may permit member-level unknown access.

### (c) Evaluate each member through a plugin-owned sender decision before aggregate admission

Mirror the current `toolsBySender` equality check:

```text
memberResult = plugin.resolveTurnSenderDecision(memberIdentity, turnContext)
aggregateBaselineResult = plugin.resolveTurnSenderDecision(senderlessBaselineContext, turnContext)
member joins aggregate only when results are equal
```

Minimal contract requirements:

- A pure synchronous/eager or bounded async evaluator exposed by plugin registration; no general replay of hooks with side effects.
- Stable result for capability/allow/deny decisions.
- Exact member identity plus account/channel/room facts.
- Fail closed on unresolved, thrown, timed-out, or incompatible policy shape.
- Core equality check before queue batching and provenance retention; leave mismatch member on an individual turn.

- Cost: highest up-front contract and migration cost, but precise and compatible with aggregate for equal-membership results.
- It can keep aggregation on for sender identities that resolve to the same capability baseline, while excluding divergent or unreadable sender policy.
- It is the only design here that can preserve both fleet aggregation and a concrete per-member plugin decision, provided plugin evaluators cover the actual plugin boundary.

## Recommendation

**Recommend (c), fail closed, with a minimal turn-time sender-decision declaration/capability as the registration owner.**

Core should:

1. Require active turn-time sender-sensitive plugins (hook/tool/channel/runtime surfaces) to register a pure `resolveTurnSenderDecision` operation and declare it in manifest/runtime metadata.
2. Before an aggregate batch, evaluate that operation against each member and against the senderless aggregate baseline.
3. Admit the member only when both decisions are equivalent; exclude thrown/unreadable/mismatched members and leave them on individual turns.
4. Default undeclared third-party plugins with sender-bearing registrations to individual turns; do not infer safety from hook name alone because plugin code decides semantics.

This keeps aggregation on for members that genuinely have the same plugin decision, including Discord policies whose member-specific and wildcard/base decisions can be proven equal. It also prevents the cut blocker because any specific sender denylist mismatch, unknown fallback, owner/admin gate, or unreadable evaluator stays out. Until the evaluator contract exists and is migrated, (a) is the safer interim default; (b) alone is unsafe and should not be credited as a cut fix.
