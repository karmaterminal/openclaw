## Ranked candidate models

1. **Matrix room-history/agent-watermark model — best**
   - Only authorized mentions/triggers become turns; all other room messages go into the room history queue.
   - The trigger reserves/snapshots history, and the per-agent watermark advances only after successful reply/adoption completion up to that snapshot; concurrent mid-turn messages remain new.
   - Real sender identity is preserved on every queued history entry; the bot principal is separate from those sender facts.
   - Multi-sender trigger authority: each actual trigger still authorizes one turn, but the core can keep owner/principal facts separate in session/route state.

2. **LINE reserved-history model**
   - Best for bounded webhook ambiguity and parallel active room turns: reserved entries are rendered once, committed/released per turn, and other reserved/overlapping deliveries cannot double-consume them.
   - The gap is no explicit per-agent seen/new watermark; the model is less precise for multiple agents sharing a room.

3. **Telegram/WhatsApp/Slack/Feishu/MSTeams/Signal/iMessage same-sender debounce model**
   - Avoid one-turn-per-fragment and sometimes coalesce text/media.
   - Same-sender keys preserve attribution; the waiting/active-turn lane can steer/control normal work.
   - They do not solve the N-sender room problem: sender IDs intentionally separate keys. Slack and WhatsApp additionally force pending same-room sender keys before cross-sender merge.

4. **Google Chat/IRC/Zalo direct event models**
   - Safest to assess as mention-gated admission but no adapter-level room coalescence. N addressed senders implies N turns unless core queue policy changes.

## Best exact model and mapping onto Discord rooms

The best model for Discord is **Matrix's two-layer room model**:

1. **Admission layer:** Discord preflight continues to admit only policy-authorized addressed/group events; unmentioned events become room-history entries instead of turn dispatch.
2. **History layer:** Discord already has a per-session/channel snowflake watermark; extend it to room/thread scope, so every trigger captures an arrival snapshot. The watermark advances only on successful agent completion and never to a later mid-turn message.
3. **Trigger layer:** Preserve real Discord sender IDs/principals on each new/seen history entry and on the triggering event. The triggering event can create one turn even when multiple sender blocks arrived before it.
4. **Burst rule:** Within a room burst:
   - ambient/unmentioned sender messages: append one history entry each, dispatch no turn;
   - addressed/mentioned messages from one or more senders: create trigger turns only for the addressed messages, not for every ambient message;
   - a future addressed trigger renders the bounded new/seen snapshot once, not duplicated as both history and separate sender turns.

The exact Discord implementation is already close:

- dispatcher key: `extensions/discord/src/monitor/message-dispatcher.ts:96-145`;
- batch flushing and trigger preflight: `...message-dispatcher.ts:220-245`;
- run queue/adoption comments: `extensions/discord/src/monitor/message-dispatcher.ts:258-294`;
- room history/history marker/watermark: `extensions/discord/src/monitor/room-history-watermark.ts:1-16,31-55,64-133`.
- Matrix parity reference: `extensions/matrix/src/matrix/monitor/room-history.ts:1-16,220-260,294-338`.

This is a **room-history aggregation lane**, not a sender replacement. It is different from a sender-keyed debounce: the history entries avoid turns; the real sender facts remain available to policy.

## Authority and least-authority aggregate comparison

The least-authority aggregate design 🌊 is safer about tools in one sense: it is owner-separate and aggregate input has no individual sender principal. It also necessarily loses direct principal-attribution for tool authorization and cannot grant an aggregate-triggered tool any power based on one anonymous/member message.

Discord's Matrix-style mapping keeps both facts:

- owner messages remain individually `senderIsOwner`/owner-authorized and separate from non-owner messages;
- aggregate history carries sender labels/context but the actual trigger principal is the event that addressed the bot;
- tool calls made on an owner-triggered turn may use owner authority only according to the existing core owner/authorization composition, not merely because other room text was present;
- aggregate/no-principal text is supplemental context, never synthesized authorization.

Compared to 🌊:

- 🌊 wins on blast radius: aggregate has no sender principal, so ambient content cannot directly trigger sender-specific tools.
- Matrix-style Discord wins on fidelity and least surprise: real sender and owner facts survive, while room-burst ambient history is not turned into a sender principal. Addressed owner and non-owner events remain distinguishable.
- The required design trade is therefore: **owner authorization is evaluated on the exact trigger; ambient/history entries are context and cannot elevate sender authority; tool policy sees senderIsOwner/principal from the trigger, not from the aggregate transcript**.

Do not bypass `resolveFollowupDeliveryStorageKey`/`resolveFollowupAuthorizationKey`; those core keys intentionally keep sender/auth facts separate. The adapter should only change admission/history rendering and burst aggregation, not downgrade the core principal.
