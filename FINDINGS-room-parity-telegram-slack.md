## Discord gap

### Telegram and Slack mechanisms Discord lacks, or Discord is poorer

1. **Slack thread participation as an implicit/broad mention escape: Slack only requires explicit bot mention to escape unmentioned room gates in a thread, while preserving thread participation routing.** Discord lacks this Slack-specific thread participation policy granularity (`extensions/slack/src/monitor/message-handler/prepare.ts:907-929`, `prepare-thread-mentions.ts:31-69`; Discord has thread routing/mention facts but not Slack's explicit `implicit_thread` equivalent in the same table).
2. **Slack bot mode has three native values with per-room overrides and bot thread context; Discord also has the mode, so this is parity rather than Slack-only.** Discord covers `allowBots=false/all/mentions` and loop protection, while Slack adds per-room/account `allowBots` precedence and explicit bot-self thread exclusion (`prepare.ts:275-310`; `prepare-room-history.ts`).
3. **Telegram has a sender-keyed inbox debounce with album/forward lanes, plus explicit quiet-window max wait and 12-entry/50k text batching.** Discord and Slack both debounce sender keys, but Telegram's forward burst lane and text-fragment long-message limits are specialized Telegram native mechanisms (`telegram` buffer).
4. **Slack reply anchoring distinguishes top-level `off` from first/all/batched thread delivery, and Slack's thread root resolver guards root-vs-child timestamps.** Discord reply behavior has no Slack `replyToMode=first/batched` thread contract; this is Slack mechanism Discord lacks (`extensions/slack/src/thread-ts.ts`).
5. **Telegram has durable-before-ack polling/webhook with offset advancement only after spool commit and webhook 200 only after spool write.** Discord/Slack are also durable, but Telegram documents and enforces this exact transport invariant across polling and webhooks (`extensions/telegram/AGENTS.md`, `telegram-ingress-drain.ts`).
6. **Telegram always maintains bounded rolling group-history, with no destructive clear and a self-entry watermark view.** Discord/Slack also have history, but Slack's room-history transport has configurable suppression and Discord has more REST-based snapshot/recovery logic; Telegram's "always on, historyLimit only" is the simpler mechanism for room context (`extensions/telegram/AGENTS.md`; `bot-handlers.message-context.ts:375-420`).

### Discord mechanisms Telegram/Slack lack, or Telegram/Slack are poorer

1. **Discord stale ambient backlog preflight is better protected:** it tombstones eligible ambient rows older than 15 minutes before dispatch, preserving mentions/replies/audio/principal intent. Telegram/Slack only have general 8-attempt/24-hour ingress retry policy; Slack/Telegram have no dedicated pre-claim stale ambient disposition with mentions/a few exemptions (Discord `ingress-stale-policy.ts:14-17`; Telegram/Slack use core retry only).
2. **Discord loop protection suppresses bot-to-bot loops before media/download/turn work; Slack only has allowBots modes/self filtering, with no same explicit loop-state mechanism found; Telegram has no allowBots/l​oop mechanism found.** (`extensions/discord/src/monitor/message-handler.preflight.ts:741-754`; Slack `prepare.ts:294-310`).
3. **Discord own-message filtering happens both before debounce and in preflight, preventing self traffic from consuming debounce capacity; Telegram outbound history cache does not establish an equivalent inbound bot-self filter, and Slack preflight self filtering is later than debouncer capacity but it keys bots separately.**
4. **Discord reply/debounce key includes reply target in addition to author/channel, which reduces incorrect cross-conversation batching. Slack keys by thread/sender, Telegram keys by chat/topic/sender; Discord's explicit reply-target split is strongest for replies.**
5. **Discord stale-policy frame validation is stronger before claim: it requires a fully readable stored gateway frame and performs the same mention/text projection as preflight.** Telegram/Slack lack this channel-specific stale classifier, but their queue codecs and mention gates are still valid at their respective boundaries.

## Promising parity fixes for Discord

1. **Forward Telegram/Slack-style explicit `allowBots` mention mode consistency and loop exposure into one documented shared policy.**
   Owner: `src/channels/inbound-event/classification.ts` plus `extensions/discord/src/monitor/message-handler.preflight.ts` / Slack/Telegram config schemas.
   Scope: fork plus upstream host/channel-policy contract if config semantics are common.
   Discord already has the modes; Telegram lacks the capability. The fix is mostly upstream policy hardening/documentation, plus a Telegram `allowBots` config implementation if desired rather than accidental bot-turn acceptance.

2. **Add Telegram/Slack-style group-history watermark/seeding guarantees for Discord ambient entries.**
   Owner: `extensions/discord/src/monitor/message-handler.context.ts`, `message-handler.recent-history.ts`, and Discord pending-history implementation.
   Scope: fork code first; promote shared history/session semantics upstream only if parity tests prove the composition.
   Keep a rolling, bounded window that is not destructively cleared, includes the current room snapshot, and uses a bot/room self-entry watermark before a mentioned turn; Discord already has much of this, but no Telegram "always on/never clear" explicit invariant was found.

3. **Keep Discord's explicit 15-minute stale ambient policy, but port a general channel-neutral stale ambient + mention principal policy to Telegram and Slack.**
   Owner: Telegram/Slack ingress modules plus `src/channels/message/ingress-retry-policy.ts`.
   Scope: upstream core only for generic retry/disposition; fork/channel adapters for 15-minute room/mention policy. Discord is already ahead here.
