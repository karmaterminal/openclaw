# CAND2 → installed-build backward-compatibility rehearsal (karmaterminal/openclaw#1415)

**Verdict: ROLLBACK-SAFE-BY-DEPLOY, with one config precondition.** Both old builds (22f49a43 and
3d3364dd) read, drain, replay or reap every persisted surface that CAND2 writes differently. Every
corrupted control fails on every reader. The one incompatibility is `openclaw.json`. Both old builds
reject every new key, even one set to `false`. If a seat's config carries any of them, the rollback
deploy refuses at `config validate` before the gateway is stopped. Clear that with one of:

- strip the keys before the rollback deploy, or
- run the rollback deploy with `migrate_config=true` plus a reason. The old build's own
  `doctor --fix` removes exactly those keys and nothing else of the operator's, then validates.

The keys are `process` (the whole root key: `process.childScope.*`),
`messages.groupChat.ambientOwnerAggregate`, `messages.groupChat.ambientOwnerAggregatePeers`, and the
same two under `agents.entries.<id>.groupChat`.

No queue drain is required. Seats whose config never set those keys need no precondition.

## Rollback behavior notes (not incompatibilities)

- Old builds have no ambient owner aggregate. After rollback, room events run as individual turns. An
  aggregate interrupted at the stop stays as an `interrupted` pending-input row, visible in history. Its
  members' ingress rows are recovered and re-dispatched, as after any restart, because its
  `followup-collect:` key is not recomputable even by CAND2.
- A channel input accepted and unfinished at the stop meets the same run-identity conflict branch after
  any restart, same build or rollback. CAND2's different `senderKind` bytes can change the outcome only
  under a reused run id, which Discord turns never have (rehearsed above).
- Scoped host-exec and CLI children have no durable registration under either build. Only Codex has one,
  and the old reaper cleans it (rehearsed). They outlive a hard stop only when the owning unit was not
  verified. This is independent of rollback, and the config precondition turns the scope off anyway.

## Gaps (named, not coded around)

- The aggregate's pending input is staged with `stageSessionPendingInput` using the real CAND2 collect
  recorder's resolved message, not through the recorder's own `stageApproved` (which also binds actor and
  lifecycle). The persisted bytes are that message. The harness member rows are synthetic: random idempotency
  key, no transport. The CAND2-specific fields are carried and compared whole.
- The Discord read runs the old drain without `readPolicy`, so the old stale-ambient pending disposition
  does not run. That disposition reads the same raw fields old live payloads already carried. The claimed row
  comes from `queue.claim` (the drain's own claim format, unchanged).
- Codex: only the unverified-owner scope is rehearsed (failing `systemctl`, so no `BindsTo`). A bound scope
  stops with the unit, so the old reaper takes its trivial dead-process branch.
- The webhook row is built with the real `buildChannelUserTurnSender` from a context carrying CAND2's webhook
  `SenderIsBot` value. The Discord context builder itself is not run end to end.
- No live gateway, seat, model turn or Discord transport was used (workorder: isolated temp state only).
