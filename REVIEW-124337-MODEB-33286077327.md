## Why `dist/build-info.json` disappeared

The runtime pretest itself did not omit the file. On both successor and pinned
upstream, `pnpm build` completed `write-build-info`
(`scripts/build-all.mts:245`) and the file existed.

The exact workflow harness then ran
`restore_upstream_plugin_discovery`, which removes `dist/extensions` and
`dist-runtime/extensions`. That deliberately makes the runtime look stale.
`scripts/run-node.mts:698` detects the missing bundled plugin entry and its
local rebuild invokes only `scripts/tsdown-build.mts --no-clean`
(`scripts/run-node.mts:140`, `scripts/run-node.mts:1734`). It synchronizes
runtime artifacts and stamps but does not run the full build's
`write-build-info` step. The partial build drops `dist/build-info.json`, so both
Gateway tests fail before exercising Gateway behavior.

The successor and pinned upstream have byte-identical `run-node`, Vitest,
test-project, build-all, and tsdown-build blobs. Exact controls produced the
same transition on both refs: full build exit 0/file present, test-launcher
partial rebuild/file missing, test exit 1.

## `hosted-batch-009` timeout

The route planned three shards with two concurrent slots:

| Shard                              | Planned seconds | Observed outcome                    |
| ---------------------------------- | --------------: | ----------------------------------- |
| `extensions`                       |             182 | repeatedly stalled; no valid result |
| `agentic-commands-doctor-whatsapp` |              32 | passed in 5 seconds                 |
| `core-runtime-infra-cli-ui`        |              13 | never launched                      |

The planned job duration was 437 seconds concurrent (664 seconds serial), but
the job had a 90-minute ceiling. The extension shard repeatedly reached the
same terminal visible area (`sglang` and
`cloudflare-ai-gateway/provider-discovery.contract.test.ts`), then emitted no
output for 300 seconds. Diagnostics showed the Vitest parent still consuming
84-95% CPU with about 6.6-6.8 GiB RSS and zombie children. No single test can be
named from the available process diagnostics; the evidence proves a
repeatable suite/order/load stall, not a normal slow completion.

Two retry layers amplified it:

1. `scripts/run-vitest.mjs` retried a no-output-killed config internally.
2. The bootstrap runner treated signal exit 143 as retryable and retried the
   full extension shard.

Four extension attempts reached the same stall area before the outer runner
announced retry 3/3. The Actions 90-minute timeout cancelled the batch before
that third outer attempt could run.

The bootstrap batch worker pool also reaps the oldest PID when both slots are
occupied. It waited on the long-running first `extensions` PID even after the
WhatsApp shard completed, so `core-runtime-infra-cli-ui` never started. The
cancelled step then could not write `batch-rc`; the uploaded receipt had
`step_outcome=cancelled`, leaving aggregate validation at 68/69 valid receipts.

Classification: **environment/order/load-sensitive extension-suite stall plus
harness/artifact-contract failure**. It is not a pass, not a single proven
hanging test, and not candidate-owned. The 182-second extension weight is
materially stale relative to every observed attempt.

Candidate ownership is excluded by routed owner evidence, not merely by the
last visible test name:

- `vitest.extensions.config.ts` explicitly excludes the Feishu, Mattermost, and
  Microsoft Teams roots that contain the PR's changed plugin tests. The config
  is byte-identical on successor, pinned upstream, and component parent.
- The exact run's candidate-owning shards all passed: `channels` 1,252/0,
  `agentic-plugin-sdk` 961/0, `extension-feishu` 1,899/0,
  `extension-mattermost` 836/0, and `extension-msteams` 1,551/0.
- The terminal `sglang` and `cloudflare-ai-gateway` provider-discovery test
  trees contain no reference to any candidate-changed path.
