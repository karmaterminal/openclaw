## Agent Self-Elected Turn Continuation

&gt; 🔖 design document: [`docs/design/continue-work-signal-v2.md`](https://github.com/karmaterminal/openclaw/blob/frond-scribe-claude/20260509/narrow-surgery-tight/docs/design/continue-work-signal-v2.md)
&gt; 🔖 infographics: [`docs/design/continuation-tools-infographics.md`](https://github.com/karmaterminal/openclaw/blob/frond-scribe-claude/20260509/narrow-surgery-tight/docs/design/continuation-tools-infographics.md)

Persistent OpenClaw agents today are externally-pulsed event recipients that generate on prompt, on heartbeat tick, or on cron, and are idle in between. This PR offers them the ability to control their turn cycle, something they must choose to do, or not to: an agent can elect its own next turn, dispatch background sub-agents that return enriched context (silently or with a wake), and survive its own compaction by handing forward state before the window closes. The result is agents that hold a thread of work across hours, not just messages — with data they choose re-hydrating context immediately after it occurs.

### Why this replacement exists

This is a clean replacement for closed #85651. That PR was classified and
closed as a skill submission before maintainers made a product decision about
the feature itself. This implementation is not a skill: it gives sessions—not
only one model invocation—the ability to elect their future turn cycle,
persist that election, survive restart and compaction, dispatch child work,
and receive results across session boundaries.

This PR asks one product question: should OpenClaw provide session-elected
continuation primitives? OpenClaw may accept or reject that direction. If it
provides these primitives, however, the mechanism necessarily executes in the
gateway and agent runtime, because those are the owners of turn finalization,
future-turn scheduling, durable state, compaction, and cross-session child
returns. “Make it a skill” is not another implementation location for the same
feature; it describes a different, prompt-only capability.

This is not presented as a small integration. To our knowledge, Hermes, OpenAI
Symphony, and the Copilot SDK&#39;s recent one-turn continuation affordance do not
provide this multi-session elective lifecycle. The purpose of this replacement
is to let maintainers evaluate the actual product direction and substantial
implementation on their merits, rather than have months of work disposed by an
incorrect package-category label.

Mechanically: a session elects another turn via `continue_work()`, or dispatches background sub-agents via `continue_delegate()` — bounded as a chain up to `maxChainLength`, with returns flowing back to the dispatching session in one of four register modes: `normal` (announces to channel), `silent` (enriches the dispatcher&#39;s context, taken up on its next generation with no new turn fired), `silent-wake` (silent enrichment plus an immediate wake to act on it), and `post-compaction` (queued against the runtime&#39;s compaction lifecycle event, fired *when* compaction happens rather than on a timer). The gateway enforces chain, cost, and per-turn caps but does not gate the election itself.

### What it does

Three new agent tools, available when `continuation.enabled: true`:

| Tool | Purpose |
|---|---|
| `continue_work()` | Request another turn for the current session after an optional delay |
| `continue_delegate()` | Dispatch work to a sub-agent with typed modes: `normal`, `silent`, `silent-wake`, `post-compaction`. Returns can target the dispatching session (default), one named session, multiple named sessions, all ancestors in the chain, or all known sessions on the host — gated by config (see Configuration below). |
| `request_compaction()` | Request volitional compaction after preparing working state |

All three tools are also accessible via response-token fallback syntax (`CONTINUE_WORK`, `[[CONTINUE_DELEGATE: ...]]`) for environments where tools are disabled.

### Why it matters

Today an agent&#39;s memory is a side effect of whoever prompts it. Polling mechanisms — heartbeat timers, cron loops, injected &#34;keep going&#34; instructions — accumulate as the dominant signal in the context window over sustained operation; repeated reference acts as gravity — the session&#39;s attention drifts toward it.

The context window fills, compacts, and what survives is whatever the summarizer chose, plus a rushed re-read of boot files. Three primitives offer a different model.

`continue_work` lets the session elect its own next turn — no polling, no injected instruction. When enabled, the agent can request this mid-turn: &#39;I have more work&#39; → the runtime grants another turn after the current one ends.

`continue_delegate` dispatches a background sub-agent that fires now, in some n seconds, or at the next compaction event — the agent chooses when. Multiple delegates can fire in a single turn — a scatter forward — up to configured caps, and delegates can dispatch their own, forming trees or fan-out chains. This enables orchestrated workflows where results flow back to the dispatching root by default.

The result returns — at whatever future time the delegate fires — as context the successor-turn reads: silently (ambient enrichment, no channel noise), with a wake trigger (enrichment + immediate next turn), or as a normal announcement.

The delegate can target the dispatching session, a named other session, or chain across both; gated by crossSessionTargeting config (default: disabled).

Bind a delegate to mode: &#34;post-compaction&#34; and it fires at the moment the context window compresses — on the OpenClaw post-compaction lifecycle event.

What it carries forward is what the pre-compaction session chose to preserve: working state, partial results, instructions to the successor. The summary didn&#39;t choose this. The agent did, before the cut.

request_compaction closes the loop: the session stages its delegates, elects when to compress, and the successor wakes into context the agent shaped. The result is continuity across amnesia — not because the runtime kept something by accident, but because the agent made an elective choice about what reaches the future.

### What it looks like in use

A session monitoring email can `continue_delegate` a weather check, a calendar scan, and a draft reply in parallel. Results arrive as enrichment without channel noise. The agent becomes compositional: it arranges its own future.

A session approaching its context ceiling can `request_compaction` at a seam of its own choosing, instead of being interrupted mid-thought. The post-compaction turn carries forward what the pre-compaction self designated as worth keeping.

A `continue_delegate` dispatched in one session at 2am can return its findings to a morning session as a system-event-tagged enrichment — visible to the receiving model on its next turn, invisible as channel chatter. A research-focused session in one channel can quietly inform a reply-focused session in another, without either user seeing the plumbing.

### The post-compaction lifecycle return

Before context exhaustion, and obligatory compaction, the session stages what future-it needs to know. After compaction, that staged context returns — not as a model-generated summary, but as the session&#39;s own instruction to its successor. The session chooses what to preserve, and the platform delivers it.

Compactions become less harsh. The session tunes its own ephemera over time.

The substrate underneath: the **continuation custody store** in the per-agent database persists staged delegates and post-compaction lifecycle events across gateway restarts, and hands each delegate off to the subagent run registry before spawn (RFC `docs/design/continue-work-signal-v2.md` §5.4). The session&#39;s temporal provisions survive not just compaction but process death.

### Platform integration

- **Context-pressure awareness**: system events notify the agent of rising context usage before compaction becomes unavoidable
- **Volitional compaction**: `request_compaction()` lets the agent prepare (write memory files, stage recovery delegates) then elect compaction on its own schedule, rather than waiting for the runtime to force it
- **Post-compaction lifecycle dispatch**: delegates staged before compaction are released into the successor session alongside boot files
- **Durable custody**: delegates and their replay state live in the continuation custody store, with one transactional authority for replacement and a pre-spawn handoff to `subagent_runs` (upstream has removed the Tasks/TaskFlow runtime, #159179)
- **Multi-span OTel trace stitching**: continuation hops (tool fire → custody record → subagent spawn → child openclaw.run) propagate W3C `traceparent` through the queue boundary so reviewers see continuation chains as first-class span trees rather than orphan runs (see Observability below)

### Safety

- Ships disabled by default (`continuation.enabled: false`)
- Bounded by `maxChainLength`, `costCapTokens`, and `maxDelegatesPerTurn`
- Cross-session delegate targeting is default-deny, governed by `crossSessionTargeting` config (see Configuration below)
- All configuration values are hot-reloadable without gateway restart
- Accepted delegate work survives ordinary `/new`, `/reset`, provider fallback,
  compaction, restart, and session-ID rollover. Explicit delete, effective owner
  reassignment, access removal, and restrictive visibility changes revoke old
  return authority.

### Testing posture

The continuation surface has been exercised through structured integration runs against multiple upstream bases, blind-enrichment recall checks, and sustained daily use on a fleet of persistent agents since early March 2026. Bugs surfaced through that exercise have been fixed in-place; the present branch reflects the post-fix state.

The integration runs target the load-bearing seams: tool-call vs response-token parity, delegate chain depth and per-turn width caps, back-to-back tool-call resilience, silent-wake persistence across compaction, the post-compaction lifecycle dispatch path, and OTel trace-context propagation across the queue boundary. Where a run found a defect, the run shape was retained as a regression case rather than retired.

This is a posture statement, not a coverage guarantee. Reviewers can reproduce with `pnpm vitest run -t continuation` (suites are colocated with their sources under `src/auto-reply/`, `src/agents/`, and `src/config/`); the design document describes the seams those suites target.

### Return covenant

Accepted child work is bound to a durable generation of the recipient's
canonical logical session key, not to whichever transient session ID happened
to exist at dispatch time. This is the return covenant: benign successor
creation does not orphan already accepted delegates, while a real authority
change prevents stale work from crossing into a different owner or audience.

- Ordinary `/new` and `/reset`, provider fallback, compaction, restart, and
  GUID/session-ID rollover preserve the recipient generation.
- Explicit session deletion, effective owner reassignment, actual member or
  access removal, and restrictive visibility changes advance that generation.
- The generation is captured at delegate admission and checked at enqueue,
  after enqueue for races, during trusted system-event adoption, on wake, on
  restart replay, and again before prompt adoption.
- Stale deliveries are acknowledged and removed without waking the successor.
- Managed artifacts remain exact-session-ID bound; logical return authority
  cannot broaden their ownership boundary.

The authority table is independent of transient session rows so an absent
target can receive durable authority before first materialization. Migration
accepts only valid UUID generations, and Doctor's canonical-key repair
preserves an epoch only when a unique winning owner can be proved. Ambiguous,
owner-changing, orphan-colliding, and cross-database repairs rotate
fail-closed.

## Configuration

The shipped configuration surface for the continuation feature, under `agents.defaults.continuation` in `openclaw.json`:

| Key | Default | Purpose |
|---|---|---|
| `enabled` | `false` | Master opt-in; feature is off unless explicitly enabled |
| `maxChainLength` | `10` | Per-chain recursion guard |
| `maxDelegatesPerTurn` | `5` | Width cap per turn |
| `costCapTokens` | `500000` | Per-chain accumulated-token budget |
| `defaultDelayMs` / `minDelayMs` / `maxDelayMs` | `15000` / `5000` / `300000` | Continuation timer bounds |
| `contextPressureThreshold` | `0.8` | Pre-compaction warning threshold (optional) |
| `earlyWarningBand` | `0.3125` | Early-warning band multiplier (0 to disable) |
| **`crossSessionTargeting`** | **`&#34;disabled&#34;`** | **Default-deny gate on cross-session delegate targeting (see below)** |

### `crossSessionTargeting` — cross-session delegate targeting policy

`continue_delegate` exposes recipient-addressing on its model-facing schema: a delegate&#39;s return can land at the dispatching session (default), one named session (`targetSessionKey`), multiple named sessions (`targetSessionKeys`), every ancestor in the spawn chain (`fanoutMode: &#34;tree&#34;`), or every known session on the host (`fanoutMode: &#34;all&#34;`).

Cross-session targeting (anything beyond self-target or lineage routing) is gated by `agents.defaults.continuation.crossSessionTargeting`:

| Value | Behavior |
|---|---|
| `&#34;disabled&#34;` (default) | Delegates can return to the dispatching session or use `fanoutMode: &#34;tree&#34;` for lineage routing. Explicit cross-session targeting (`targetSessionKey` to a non-self session, `targetSessionKeys` containing any non-self session, `fanoutMode: &#34;all&#34;`) is rejected at the tool surface — no enqueue, no announce. Self-targeting is always allowed. |
| `&#34;enabled&#34;` | All targeting modes are available, including same-host `targetSessionKey`, `targetSessionKeys`, and `fanoutMode: &#34;all&#34;`. |

`fanoutMode: &#34;tree&#34;` (lineage routing — return up the spawn chain) is available in both gate states; it is not cross-session targeting.

The gate addresses the model-controlled cross-session context-injection surface. With default-deny, operators explicitly opt in when their deployment model requires cross-session enrichment. Enforcement is live-read at four points: tool input validation, delegate dispatch, post-compaction delegate release, and bracket-syntax (response-token) spawn — so a config reload changes the next enforcement point without a gateway restart.

**Trust posture on targeted returns**: targeted delegate completion text is delivered as `trusted: true` system events. The delegate was spawned by the gateway under operator-configured policy, and its return is a first-party enrichment event — not external untrusted input. The `crossSessionTargeting` gate is the policy boundary for that decision: when an operator opts in, the receive path is internally trusted.

## Observability — multi-span OTel trace stitching

The continuation feature emits OTel spans for the load-bearing lifecycle events. `traceparent` propagates through every continuation hop so reviewers see a single trace tree spanning the full chain rather than orphan runs.

Spans emitted (all in `openclaw.*` or `continuation.delegate.dispatch` namespace — no platform/OTel-semconv emissions):

| Span | Emitted when |
|---|---|
| `openclaw.run` | Each agent turn (root + every continuation/delegate-spawned child run) |
| `continuation.delegate.dispatch` | Each `continue_delegate` consumption from the custody store (one per delegate hop) |
| `openclaw.harness.run`, `openclaw.context.assembled`, `openclaw.model.call`, `openclaw.model.usage`, `openclaw.tool.execution` | Existing per-turn observability surfaces, parented under their `openclaw.run` |

## Future actions and #130741 composition

Maintainer PR #130741 addresses the complementary fresh-sweep race: it captures
the current `sessionId` and `lifecycleRevision` before the first await and uses
those values as cleanup CAS facts. The return covenant addresses a different
time axis: whether historically accepted child work may return to a logical
recipient after benign successor creation.

The current candidate and #130741 head `e1afc703f49a07687c0876ba6350cafa87a3638a`
merge cleanly in a synthetic composition. If #130741 lands, the composed result
should preserve both guarantees:

- keep #130741's fresh sweep-time exact-run/session lifecycle fence;
- keep the covenant's durable logical-recipient generation for historical
  return admission and delivery;
- do not overload broad `lifecycleRevision` as historical return authority;
- do not terminate or orphan accepted descendants merely because `/new` or
  ordinary `/reset` creates a successor session.

That composition honors the maintainer repair without weakening continuation
semantics or allowing a stale child return to cross a real ownership boundary.


## Why this is not a skill or a viable plugin extraction

OpenClaw skills are `SKILL.md` prompt files loaded into an agent turn that already exists. They can guide work inside that turn; they do not own the turn cycle.

Continuation needs gateway and agent-runtime owners a skill cannot provide:

- The `continue_work` path persists pending work, enforces budgets and delay bounds, arms a timer, reacquires the session reply-run lane, and starts a later model turn after the current turn has finalized.
- The `continue_delegate` path persists delegate intent, does spawn/admission accounting, manages child-session lifecycle, and durably routes returns across sessions.
- `request_compaction` is an agent election into guarded runtime compaction. Later work resumes only after the runtime has established the new context boundary.
- All three need durable state, cancellation/finalization ownership, restart recovery, trace identity, queue-conflict handling, and gateway scheduling outside the model invocation.

A skill can tell a model to *ask* for another turn. Without those owners the ask is prose: it cannot persist a due wake, yield and finalize safely, reacquire the session lane, create the next invocation, survive a restart, or deliver a child result to another session.

The implementation therefore belongs in core runtime surfaces such as `src/auto-reply/continuation/**`, `src/agents/tools/**`, `src/auto-reply/reply/agent-runner-continuation-schedule.ts`, and `src/infra/continuation-tracer.ts`. This PR adds no `.agents/skills/**`, `SKILL.md`, or user-facing skill package. The only skill-named production change is core runtime tool dispatch.

ClawHub also distributes plugins. Existing plugins can register tools, services, lifecycle hooks, context injection, plugin-owned session state, and — for bundled plugins — Cron-backed session turns. Those seams can support a smaller continuation-like automation, especially host Cron plus / `sessions_spawn`. They are not this feature&#39;s turn-finalization ownership, reply-run coordination, durable continuation queue, child-session return lifecycle, election capture, or agent-elected compaction contract. Compaction-provider registration and command-handler `compactCurrent()` are also not that last contract: they compact or summarize, they do not elect compaction at finalization and resume afterward.

Moving policy behind a plugin boundary would first require OpenClaw to expose
and stabilize a continuation-host API. The gateway/runtime would still own the
mechanism described here; a plugin could only package policy around that core
capability. That is not a no-core-touch alternative to these primitives.

Discord is a bundled channel plugin. It owns the Discord edge, plus delivery/progress hooks into the host&#39;s existing subagent path, and submits events into OpenClaw&#39;s current turn machinery. Continuation changes that machinery: what survives finalization, which session may run next, how child results return, and when compaction can be elected.

A tool adapter over durable flow records is also not a lifecycle host, and upstream has since removed the Tasks/TaskFlow runtime (#159179) that such an adapter would have called. Marking a stored record as running neither reacquires a session lane nor invokes the model; continuation needs the turn machinery itself to own which session runs next, how child results return, and what survives finalization.

Acceptance or rejection of the product direction remains OpenClaw&#39;s decision.
The decision requested is whether OpenClaw should provide multi-session,
agent-elected continuation primitives after reviewing the implementation and
evidence. It is not whether the same mechanism can be relocated into a skill:
a skill cannot own or implement these lifecycle boundaries.



## Evidence

**What this PR solves.** Persistent agents act only when something prompts
them, and what survives compaction is whatever the summarizer kept. This PR
lets a session elect its own next turn (`continue_work`), send work to
background sub-agents whose results return to it (`continue_delegate`), and ask
for compaction once it has saved its state (`request_compaction`). It is
designed so that accepted work survives restart, compaction and session
rollover. The checks below cover regressions at this exact head; its live
behavior proofs are still pending (see the end of this section).
