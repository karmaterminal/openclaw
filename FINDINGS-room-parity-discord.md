## Nine-cell parity grid

### Core and shared queue policy

1. **Classification:** `InboundEventKind` is set by `resolveUnmentionedGroupInboundPolicy` / `classifyChannelInboundEvent` in core. A group/channel unmentioned message is `room_event` only when the group policy selects `room_event`; a mention, command, or native source promotes it to `user_request`. Direct/group-DM traffic uses `user_request`. [traced: `src/channels/inbound-event/classification.ts:6-33`, `src/channels/inbound-event/classification.ts:35-48`]
2. **Turn or ambient:** With `unmentionedInbound: "room_event"`, Discord/Slack/Telegram/WhatsApp/LINE adapters can admit the message as a room turn; but some rendering paths also keep it in group history. Whether it starts a turn is determined by mention gating and the channel adapter's dispatch policy, while core `room_event` suppresses visible delivery. [traced: classification above; `src/auto-reply/reply/followup-turn-execution.ts:89-93`]
3. **Bot authors:** Platform policy varies; Slack has `allowBots` with `off`/`all`/`mentions` and owner/loop protection [traced: `extensions/slack/src/monitor/message-handler/prepare.ts:275-306`, `extensions/slack/src/monitor/message-handler/prepare.ts:907-910`]. Discord and Telegram have bot/self filters, but Discord's transport admits self rows before dispatch filters them. [traced: Discord `extensions/discord/src/monitor/message-handler.preflight.ts:242-245`; `extensions/discord/src/monitor/message-dispatcher.ts:322-324`]
4. **Debounce:** shared keyed debounce serializes by key, but implementation adds platform identity fields. [traced: `src/auto-reply/inbound-debounce.ts:150-260`]
5. **Durable ingress:** shared core ownership uses `exclusive` admission and turn-adoption settlement. Discord/Slack/WhatsApp/Telegram/LINE all use durable/funnel mechanisms in their adapters; Telegram and WhatsApp retain separate claims during debounce/release occupancy. [traced: `src/channels/AGENTS.md` contract; `src/channels/message/ingress-drain-lifecycle.ts:53-58`; Discord `extensions/discord/src/monitor/ingress.ts:186-198`; Slack `extensions/slack/src/monitor/ingress.ts:436-440`; WhatsApp `extensions/whatsapp/src/inbound/durable-receive.ts:102-126`; Telegram `extensions/telegram/src/telegram-ingress-drain.ts`]
6. **Queue mode:** room events are forced to `followup` during source policy update regardless of configured `collect`; follow-up collector rejects any source with `currentInboundEventKind === "room_event"` as an individual collect drain. [traced: `src/auto-reply/reply/get-reply-run-admission.ts:151-155`; `src/auto-reply/reply/queue/envelope.ts:259-268`; mailbox gate `src/sessions/session-controller.mailbox-dispatch.ts:120-131`]
7. **Stale policy:** core/default queue policy is separate from the Discord stale ambient overlay. Discord has a 15-minute plugin-owned pre-claim policy for ambient backlog. It requires the live channel policy to classify the row, and protects mentions/replies/addressed intents under its detailed preflight parity logic. No comparable general stale-ambient overlay was found in the other platform implementations. [traced: `extensions/discord/src/monitor/ingress-stale-policy.ts:33-34`, `extensions/discord/src/monitor/ingress.ts:185-198`]
8. **Drain outcome:** with a burst of N room-event sources while M senders share one lane/active session, room-event sources drain one follow-up turn each, not one turn for the whole burst, because admission forces `followup` and the collect selector individually rejects them. `M` affects collect authorization keying only for eligible non-room sources. [traced: `src/auto-reply/reply/get-reply-run-admission.ts:151-155`; `src/auto-reply/reply/queue/envelope.ts:259-268`; `src/auto-reply/reply/queue/delivery-context.ts:72`]
9. **Reply anchoring:** replies are anchored through the original source/transport reply reference and policy. Each room drain has no visible reply by default (`room_event` delivery is suppressed); user-request follow-up replies anchor according to channel `replyToMode`/thread policy. Discord replies use the source message or adopted thread. [traced: `src/auto-reply/reply/followup-turn-execution.ts:89-93`; Discord `extensions/discord/src/monitor/message-handler.process.ts:148-172`, `extensions/discord/src/monitor/message-handler.process.ts:466-470`; `extensions/discord/src/monitor/message-handler.context.ts:563-564`]

## Discord gap

### Mechanisms Discord has, and where others are better

- **Discord lacks WhatsApp sender-change flush semantics at the Discord debounce boundary.** WhatsApp explicitly flushes a pending conversation debounce when `senderKey` changes (`extensions/whatsapp/src/inbound/message-debounce.ts:136-149`); Discord's shared debounce/durable claim does not provide the same sender-author-attribution split. **Gap for Discord:** multi-sender burst attribution can be combined too loosely before core, depending on key construction; the WhatsApp sender key is a concrete parity mechanism.
- **Discord stale ambient backlog is stronger than Slack/Telegram/WhatsApp/LINE in the traced composite.** Discord pre-claim can dead-letter stale ambient rows in `15 * 60 * 1,000` ms (`extensions/discord/src/monitor/ingress-stale-policy.ts:33-34`, used at `extensions/discord/src/monitor/ingress.ts:185-198`). Slack/Telegram/WhatsApp/LINE do not have a matching transport-owned stale-room policy. However this policy is still too narrow: source comments and tests identify replies, ordinary mention gating, and principal exemptions as weaknesses.
- **Discord release occupancy has parity with Slack and WhatsApp.** Discord, Slack and WhatsApp all pass `deferredLaneOccupancy: "release"` (Discord `extensions/discord/src/monitor/ingress.ts:186`; Slack `extensions/slack/src/monitor/ingress.ts:436-440`; WhatsApp `extensions/whatsapp/src/inbound/durable-receive.ts:102-126`). This fixes the old held-lane symptom but not coalescing.
- **Discord has bounded ambient group history, with Telegram and LINE stronger ownership patterns.** Discord records/replays bounded history and includes history for room events (`message-handler.context.ts:189-191`, `:580-590`). Telegram explicitly always keeps a bounded rolling group window and a self-entry watermark (`telegram AGENTS`; `group-history-window.ts:89-117`). LINE reserves overlapping history entries and commits/releases them with turn settlement (`group-history.ts:1-49`). Discord has recent history and replay cleanup but no equivalent explicit overlap reservation; overlapping replay paths can therefore be more complex. **Gap/integration risk:** Discord should reuse bounded-history invariants rather than channel-specific cleanup logic.
- **Discord self-bot filtering happens too late.** Raw `MESSAGE_CREATE` is admitted durably first (`extensions/discord/src/monitor/ingress.ts:150-205`), and the own-bot filter runs only at dispatch (`message-dispatcher.ts:322-324`). Slack's bot policy is evaluated in prepare before dispatch and exposes a loop guard (`prepare.ts:275-306`, `:907-910`; Slack `allowBots` UI hints `:73-84`). Telegram keeps bot identity in message context. **Discord gap:** own-bot frames add durable claims/backlog even though they never start a turn.
- **Discord lacks Slack's mature bot-loop/sliding-window guard and `allowBots: "mentions"` turn filtering.** Slack is the richer peer-bot mechanism: off/all/mentions plus channel override, owner presence, and pair-loop protection (`slack config-ui hints 73-84`; `prepare.ts:275-306`). Discord only exposes generic allow-bot classification/filters in its channel policy; there is no Slack-equivalent `botLoopProtection`.
- **Discord room replies are deliberately hidden while Telegram/Slack/LINE have visible-reply policy variants.** Core room delivery suppresses `room_event` final visible replies (`followup-turn-execution.ts:89-93`). Slack/Telegram explicitly expose `visibleReplies: automatic` or group/thread reply policy. Discord can still auto-thread via its own mechanism, but not act on every room burst as a visible reply. **Gap decision:** Discord lacks an operator switch for visible ambient turns, as the room-event policy is deliberately no visible reply.
- **Discord thread anchoring is rich but partitioned.** Discord supports source reply, auto-thread, adopted active-thread route and batched reply threading (`message-handler.process.ts:148-172`; `message-handler.context.ts:563-564`; `threading`). Slack also anchors by thread/parent/root, Telegram by chat/topic/message, LINE by native quote, and WhatsApp by implicit/quoted current message. Discord parity is generally good, though thread migration/active-route state is channel-specific rather than a simpler shared contract.

### Mechanisms where Discord is better

- Discord is the only platform in this trace with a plugin-owned pre-claim stale ambient policy. It can inspect payload age, live channel policy, bot identity, mentions, replies, audio and addressed intent before claim/admission (`ingress-stale-policy.ts`; `ingress.ts:185-198`). That mechanism is parity-worthy for Slack, Telegram, WhatsApp and LINE if generalized.
- Discord's release-of-deferred-lane behavior, explicitly present in the ingress drain, matches Slack and WhatsApp and avoids the old `hold` lane bug. Telegram has a similarly explicit sequential lane/laned spool, not a same-line release option.
- Discord/Slack rich mention and history policies are both per-channel and per-account scoped, unlike LINE/WhatsApp which rely on fewer group-policy surfaces.

## Drain invariant and the two load-bearing roots

For N messages from M senders:

1. Discord durable ingress can claim/defer each row with independent exclusive custody. `release` means each claim frees its lane, but does not merge sources.
2. Core classification sets `room_event`.
3. Core forces follow-up policy at admission even if `messages.queue.byChannel.discord=collect`.
4. `requiresIndividualCollectDrain` rejects room-event sources, so the mailbox claim contains one item and one model turn.

Result: **N model turns**, approximately one at a time in the active mail queue, each prompt containing one source envelope plus bounded history/reply context as applicable. A burst after the active turn ends is wake/claim-driven, not collapse-driven. Queue `cap/drop` applies per follow-up overflow but does not create one collected room turn.

## Recommended parity fixes

1. **Owner-correct core batching for compatible room events.** Change the owner composition in `src/auto-reply/reply/get-reply-run-admission.ts`, `src/auto-reply/reply/queue/envelope.ts`, and the mailbox selector if it owns the guard, so compatible room-event sources may collect while each exclusive ingress lifecycle is adopted/settled exactly once. Preserve sender/authority/room keys, one-source prompt ordering, and current drop/cap semantics. This must be upstream core, not Discord-only.
2. **Generalize stale-ambient backlog as core/plugin policy with configurable age and principal exemption.** Keep Discord's payload owner and live policy reader in `extensions/discord/src/monitor/ingress-stale-policy.ts`, but move the age/config/cap/digest contract into shared queue/ingress policy (`src/channels/message/` + queue settings). Enforce at claim time, default-preserve mention/reply/principal intent, and expose an operator-visible tombstone/dead-letter reason. This is first a fork overlay because no landed upstream equivalent is present; migrate to upstream if the contract is accepted.
3. **Drop own bot/echo frames before durable enqueue in Discord and parity ports.** Add the self filter to `extensions/discord/src/monitor/ingress.ts`/Discord admission, not only dispatch, using the known `botUserId` identity. Keep explicit bot-peer traffic governed by `allowBots`/`mentions`; do not silently change peer-bot policy. This is Discord fork code if implemented locally now; if generalized, Slack/WhatsApp/Telegram self-echo seams belong in their channel adapters while bot-loop policy remains shared at ingress configuration.
