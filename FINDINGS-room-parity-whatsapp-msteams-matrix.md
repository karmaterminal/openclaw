## Drain trace detail

1. `M/N` burst semantics are platform-specific before core admission:
   - WhatsApp: same account/conversation/sender window produces one batch; sender change flushes the current batch.
   - Teams: same account/conversation/thread/sender window produces one batch; thread/sender change splits.
   - Matrix: room ingress is ordered and serialized, then each accepted event calls core normal admission; no Matrix-specific text batch window exists.
   - Discord: every source reaches preflight/admission; passive group/channel chatter becomes `room_event`, then core forces individual follow-up drain.
2. For WhatsApp and Teams, because the batch mechanism is at ingress/debounce, one batch fan-in can settle/fan multiple ingress claims and produce one model turn.
3. For Matrix, room ingress and core queue neither declare compatible same-batch grouping nor add a Matrix room-event classification, so cross-event coalescence depends entirely on normal core queue settings and the `user_request` lifecycle. Matrix therefore does **not** have Discord’s room-event individual barrier, but it also has no guaranteed digest/coalescing mechanism.
4. For Discord, active-run follow-up queues are source-policy `followup`, not configured collect. Once idle, the same source filter prevents compatible room sources from forming one collect claim. No claimed source can collect another.

## Discord gap

### WhatsApp, Teams, and Matrix mechanisms Discord lacks or has worse

1. **WhatsApp sender-local batching of ingress entries.** WhatsApp flushes the pending batch on a sender change and combines only same-conversation entries from one sender (`extensions/whatsapp/src/inbound/message-debounce.ts:132-149`). Discord has `debounceMsByChannel` but the known room-event guard prevents queue coalescence; Discord does not batch ingress sources at the same owner boundary after admission.
2. **WhatsApp durable claims retained across a debounce fan-in.** One flush can fan multiple lifecycle claims into one dispatch and settle them together (`message-debounce.ts:42-70; durable-receive.ts:131-155`). Discord has per-source claims and per-source room follow-up turns; it lacks a channel ingress batch that fans a sender run into one turn.
3. **WhatsApp sender identity flush better protects attribution.** Sender-key flush prevents cross-sender body concatenation while still batching one sender (`message-debounce.ts:143-149`); Discord batching older/preceding source resolution is more brittle because it is blocked at queue-policy ingress rather than sender batched.
4. **Teams sender+thread debounce.** Teams keys by account, conversation, thread root, and sender, so a burst can coalesce only among the same participant in the same thread, reducing cross-attribution merges (`extensions/msteams/src/monitor-handler/message-handler.ts:610-634,639-676`). Discord has message batching of forwarded/repeated sources, but not this explicit thread/sender ingress batch key.
5. **Teams Graph/thread context.** Teams supplements pending channel history with a capped Graph `Thread history` structured context (`message-handler.ts:448-511`). Discord has recent-history recovery and thread starter context, but Teams more consistently treats a channel/backlog window and thread slice as distinct supplemental context owners.
6. **Matrix per-agent room/per-thread watermarks.** Matrix tracks independent agent watermarks over a bounded room queue and separate thread queues; snapshot advancement happens at trigger preparation, and messages arriving after the snapshot are reserved for the next trigger (`extensions/matrix/src/matrix/monitor/room-history.ts:1-18,120-190`). Discord guild histories are shared maps/hydration plus the core session history; they do not provide Matrix’s explicit per-agent consumed/upstream watermark model across a room and each thread.
7. **Matrix room FIFO ingress queue around access/history.** Matrix serializes prefix/read/mention/audio/enrichment state per room before core dispatch (`extensions/matrix/src/matrix/monitor/handler.ts:206-235`). Discord shares a durable lane but no room-history snapshot queue with an explicit per-agent watermark.
8. **Matrix bot-loop protection.** Matrix has pair-window/cooldown loop guard facts owned by the bot ingress policy (`extensions/matrix/src/matrix/monitor/handler-ingress-access.ts:117-130`) and an account/room bot allow mode. Discord has the stronger of the two policies overall (`allowBots` off/mentions/all plus loop guard), but Matrix’s room/ thread override still supplies concrete config local precedence Discord could copy for rooms.
9. **Matrix configurable bot thread mention policy.** Matrix supports `requireMentionInBotThreads` at room/account level (`extensions/matrix/src/matrix/monitor/handler-ingress-content.ts:299-308`). Discord has bound-thread and auto-thread rules, but this is a cleaner explicit room-in-bot-thread mention override.
10. **Platform-specific reply anchoring.** Teams explicitly separates thread root and reply parent (`message-handler.ts:498-502`); Matrix separates thread target from quote/reply event (`handler-context.ts:241-245`). Discord supports comparable threading/reply modes, but Matrix and Teams make the thread/reply split explicit in `reply` context.

### Discord mechanisms the other platforms lack or have worse

1. **Discord explicit ambient `room_event` classification.** Discord preflight is the only scope here that sets room traffic to `room_event` via the shared core classifier. WhatsApp, Teams, and Matrix currently hardcode accepted room traffic as `user_request` in dispatch/context.
2. **Discord richer bot policy.** Discord has `allowBots:false | true | "mentions"`, own-bot suppression, outbound echo suppression, PluralKit handling, mention-gated bot behavior, and loop guard support (`message-handler.preflight.ts:150-155,266-269,377-379,667-671`; config UI at `config-ui-hints.ts:289-295`). Matrix has room/account allowBots and loop guards but Teams and WhatsApp lack an equivalent named bot policy at this owner.
3. **Discord stale ambient backlog policy.** Discord has a 15-minute pre-claim stale ambient disposition that fails only provably mention-gated, non-thread, unmentioned backlog (`ingress-stale-policy.ts:34-36,394-475`). WhatsApp, Teams, and Matrix have no platform-parity owner that drops unmentioned ambient backlog before turn admission; Matrix startup historical exclusion is different, and WhatsApp/Teams still retain or retry rows.
4. **Discord main-room history integration.** Discord classifies room context and carries `InboundHistory`, replay history, and optional recent channel history into the room turn; context can recover and bound it (`message-handler.context.ts:188-191,402-424,580-591`). Teams and WhatsApp have bounded pending/history features, but Discord has an explicit stale/ambient/replay policy adjacent to that context.
5. **Discord principal/mention stale exemptions.** The Discord policy protects control commands, mentions, direct-open channels, and unknown/reply ambiguity (`ingress-stale-policy.ts:418-475`). WhatsApp, Teams, and Matrix have no same named principal/reply/mention pre-claim stale owner, but this implementation itself lacks a principal-author exemption (the issue comment’s proposed gap remains real).
6. **Discord outbound echo and self-loop protection.** Discord checks own author ID and recent outbound message identity before dispatch and suppresses self/webhook echoes (`message-handler.preflight.ts:150-155,172-191`; Matrix has configured-bot loop guard but no explicit outbound-echo identity pattern in the traced handler; WhatsApp/Teams lack such a clear named barrier).

## Most promising parity fixes for Discord

1. **Fix the core room-event collect/followup invariant.** Owner: `src/auto-reply/reply/get-reply-run-admission.ts`, `src/auto-reply/reply/queue/envelope.ts`, and only if needed `src/sessions/session-controller.mailbox-dispatch.ts`. Add one explicit policy: compatible room-event sources may batch in collect while each exclusive ingress lifecycle settles exactly once; active and idle paths must use the same aggregation identity. This is **upstream core** code and would fix all channels that emit room events, not a Discord-only fork patch.
2. **Add bounded ambient coalescing/digest policy by ingress lane.** Owner: `extensions/discord/src/monitor/ingress.ts` plus the shared queue/claim owner. Preserve sender/authority/thread in the collect key, coalesce at claim or debounce into one digest turn under cap/drop policy, and keep mentions/principals/control/abort claims as individual intent. This can be a **fork-owned channel fix first**, then promoted upstream as a shared queue contract if the core invariant is accepted.
3. **Complete Discord stale/principal policy and expose configurable age.** Owner: `extensions/discord/src/monitor/ingress-stale-policy.ts` and live policy/config schema. Apply the 15-minute fallback selectively to true ambient backlog, not ordinary replies, and explicitly exempt principal/owner authors and address-to-bot evidence. Make the current 15-minute hard cutoff configurable per account/channel. This is primarily **fork behavior until upstream owner shape is agreed**; the stale policy file is already Discord-owned fork/upstreamed product code.
