# RFC <-> Code Alignment Audit - continue-work-signal-v2

Scope: `docs/design/continue-work-signal-v2.md` (1400 lines)  
Code surface: continuation feature on `cael/325-canonical2` lineage, audited at pre-report SHA `1d197c8d28417e0973f728fda6daf00f2d764eeb`  
Audit date: 2026-05-01  
Lane: `frond-scribe/441-rfc-alignment-audit` (`continue-work-signal-v2`)

## Methodology

I read the RFC end-to-end, then walked the implementation surfaces named in the workorder: continuation parsing/config/runtime, continuation tools, reply-run integration, delegate dispatch, subagent announce/spawn, request-compaction, context-pressure, post-compaction delegate delivery, status rendering, session-delivery queue, heartbeat wake, and diagnostics-otel tracing. Findings below cite both RFC lines and implementation lines.

This report treats code as the current truth for shipped behavior. Where the RFC explicitly labels a surface as proposed/future, I did not count absence from code as drift; where the RFC labels a surface as shipped or implemented and code differs, I counted it as drift or over-description.

## Summary

- Class A, aligned: 12 representative findings.
- Class B, drift: 8 findings.
- Class C, depth-fit drift: 5 findings.
- Class D, under-described in RFC: 9 findings.
- Class E, over-described in RFC: 5 findings.

Overall verdict: the RFC is broadly aligned on the core continuation primitives: opt-in gating, `continue_work`, `continue_delegate`, `request_compaction`, context-pressure advisories, silent/silent-wake returns, post-compaction handoff, and guardrails. The highest-risk drift is concentrated in recent substrate/tracing evolution: the RFC overstates current `session-delivery-queue` coverage, names a span schema that is not the code's canonical schema, and describes `targetSessionKey` as an exposed descriptor seam even though the shipped `continue_delegate` tool schema has no such field.

## Class B - Drift findings

### B1 - `targetSessionKey` is described as an exposed descriptor seam, but the shipped tool schema has no field

- RFC: `continue_delegate()` "descriptor surface also includes `targetSessionKey?: string`" and rejects provided `targetSessionKey` as descriptor-only (`docs/design/continue-work-signal-v2.md:154-158`).
- Code: `continue_delegate` schema contains only `task`, `delaySeconds`, and `mode` (`src/agents/tools/continue-delegate-tool.ts:17-39`); execution reads only those fields and enqueues/stages against the implicit current `agentSessionKey` (`src/agents/tools/continue-delegate-tool.ts:80-151`).
- Drift axis: public contract / schema.
- Recommendation: update RFC to say the current shipped tool has no `targetSessionKey` parameter; local recipient is implicit from the current session. Keep explicit `targetSessionKey`/`targetSessionKeys` solely in future directions unless code adds and rejects the field intentionally.

### B2 - RFC span schema names do not match canonical code span names

- RFC: shipped span schema names include `continuation.delegate.enqueue`, `continuation.delegate.spawn`, `continuation.delegate.return`, `continuation.compaction.requested`, `continuation.compaction.enqueued`, `continuation.compaction.completed`, and `continuation.context_pressure.fire` (`docs/design/continue-work-signal-v2.md:931-949`).
- Code: canonical span union is `continuation.work`, `continuation.work.fire`, `continuation.delegate.dispatch`, `continuation.delegate.fire`, `continuation.queue.enqueue`, `continuation.queue.drain`, `continuation.compaction.released`, `continuation.disabled`, and `heartbeat` (`src/infra/continuation-tracer.ts:215-224`). Helper implementations emit those names (`src/infra/continuation-tracer.ts:390-415`, `src/infra/continuation-tracer.ts:446-477`, `src/infra/continuation-tracer.ts:602-645`, `src/infra/continuation-tracer.ts:683-723`, `src/infra/continuation-tracer.ts:754-782`, `src/infra/continuation-tracer.ts:800-838`).
- Drift axis: observability contract.
- Recommendation: replace the RFC's §6.6 span table with the code's canonical names and attributes, or rename code emitters to the RFC names before presenting the RFC as shipped-contract documentation.

### B3 - `session-delivery-queue` coverage is overgeneralized for normal silent-wake/deep-child returns

- RFC: the queue is described as the load-bearing transport for deep-child to root-session enrichment, fan-out multi-target reporting, and silent-wake without channel-message round trip (`docs/design/continue-work-signal-v2.md:430-457`).
- Code: queue storage can represent `systemEvent`, `agentTurn`, and `postCompactionDelegate` payloads (`src/infra/session-delivery-queue-storage.ts:67-96`) and post-compaction delegates use it (`src/auto-reply/reply/post-compaction-delegate-dispatch.ts:611-691`). Normal silent/silent-wake delegate returns still use in-memory `enqueueSystemEvent()` plus `requestHeartbeatNow()` (`src/agents/subagent-announce.ts:1173-1198`), and the system-event queue is explicitly in-memory/ephemeral (`src/infra/system-events.ts:1-3`, `src/infra/system-events.ts:119-140`).
- Drift axis: durability/addressability semantics.
- Recommendation: distinguish storage substrate capability from actual continuation call sites. State that post-compaction handoff is queue-backed today; normal silent-wake/deep-child enrichment still returns through system events and heartbeat wake unless/until those paths are migrated.

### B4 - Post-compaction release is queued/asynchronous, not a synchronous "released into successor" count

- RFC: staged delegates are "released into the successor session" and examples say "Consuming 1 compaction delegate(s) - dispatching alongside boot files" (`docs/design/continue-work-signal-v2.md:585-605`, `docs/design/continue-work-signal-v2.md:828-833`).
- Code: lifecycle event says "Queued N post-compaction delegate(s)" and comments define `queuedDelegates` as accepted-into-queue, pre-spawn, upper-bound semantics (`src/auto-reply/reply/post-compaction-delegate-dispatch.ts:283-314`). Actual drain is fire-and-forget and failures retry via queue recovery (`src/auto-reply/reply/post-compaction-delegate-dispatch.ts:671-691`, `src/infra/session-delivery-queue-recovery.ts:215-247`).
- Drift axis: lifecycle ordering / observability wording.
- Recommendation: update §4.4/§6.2 to use "queued for delivery into the fresh session" and document that spawn completion is asynchronous and may fail/retry after the lifecycle event.

### B5 - Durable delegate language should separate TaskFlow rows from volatile reservations/timer handles

- RFC: delayed reservations are described as recoverable delegate records backed by Task Flow, while timer handles are process-scoped (`docs/design/continue-work-signal-v2.md:321-322`, `docs/design/continue-work-signal-v2.md:757-773`).
- Code: pending delegates are TaskFlow-backed (`src/auto-reply/continuation/delegate-store.ts:1-10`, `src/auto-reply/continuation/delegate-store.ts:158-175`, `src/auto-reply/continuation/delegate-store.ts:194-239`). The delayed reservation list itself is an in-memory `Map`, explicitly volatile because timer handles do not survive restart (`src/auto-reply/continuation/delegate-store.ts:373-459`), and the type says timer reservations are volatile unless TaskFlow backing is enabled (`src/auto-reply/continuation/types.ts:62-65`).
- Drift axis: persistence semantics.
- Recommendation: preserve the TaskFlow claim for pending delegate rows, but avoid implying the exact delayed reservation/timer state is durable. Use "work survives as queued delegate intent; exact wake timing/reservation handle is process-local."

### B6 - Context-pressure pre-run path has two implementations with different preconditions

- RFC: §4.2 says pre-fire runs only when `totalTokens` and context window are present (`docs/design/continue-work-signal-v2.md:528-529`); Appendix D sketch includes `sessionEntry.totalTokensFresh` in the gate (`docs/design/continue-work-signal-v2.md:1318-1335`).
- Code: `agent-runner.ts` first imports the continuation lazy helper and gates on `threshold`, `activeSessionEntry.totalTokens`, and context window, but does not check `totalTokensFresh` (`src/auto-reply/reply/agent-runner.ts:1430-1452`). A second pre-run check immediately after uses `src/auto-reply/reply/context-pressure.ts`, which does check `totalTokensFresh === false` and mutates `lastContextPressureBand` (`src/auto-reply/reply/agent-runner.ts:1457-1498`, `src/auto-reply/reply/context-pressure.ts:38-90`).
- Drift axis: implementation topology / precondition details.
- Recommendation: pick and document the canonical pressure path. If both paths are intentional, describe their ordering and state ownership; otherwise remove or merge the duplicate in code before the RFC claims one canonical pre-run gate.

### B7 - `/status` evidence path is stale

- RFC: says the Discord/agent path is through `src/auto-reply/status.ts` and tests in `src/auto-reply/status.test.ts` (`docs/design/continue-work-signal-v2.md:846-852`).
- Code: the formatter now lives in `src/status/status-message.ts` (`src/status/status-message.ts:67-114`). The test path cited by the RFC still exists, but the production implementation path does not match the RFC citation.
- Drift axis: evidence citation / maintainability.
- Recommendation: update evidence location to `src/status/status-message.ts` while keeping the existing test citation if still relevant.

### B8 - `request_compaction()` is exposed in follow-up turns but may reject as context-unknown there

- RFC: describes `request_compaction()` as a current-session tool that works with context-pressure awareness and platform compaction (`docs/design/continue-work-signal-v2.md:183-195`, `docs/design/continue-work-signal-v2.md:530-559`).
- Code: queued follow-up turns wire the tool when continuation is enabled, but `getContextUsage()` returns `null`, producing the tool's `context_threshold` rejection for inventory-only paths (`src/auto-reply/reply/followup-runner.ts:337-352`, `src/agents/tools/request-compaction-tool.ts:156-165`). Main-session execution supplies a real ratio (`src/auto-reply/reply/agent-runner-execution.ts:1208-1221`).
- Drift axis: availability vs successful-operation semantics.
- Recommendation: add a short note that `request_compaction()` may be present on follow-up turns but reject when current context usage is unavailable; "current session only" is not the only operational precondition.

## Class C - Depth-fit drift findings

### C1 - Observability schema is discussed at contract depth, but code's contract is a different vocabulary

The RFC gives a full shipped span schema table (`docs/design/continue-work-signal-v2.md:921-949`). Code has an equally detailed but different canonical tracer vocabulary and helper-level semantics (`src/infra/continuation-tracer.ts:215-224`, `src/infra/continuation-tracer.ts:378-838`). This is not just a missing line item; the RFC depth implies downstream consumers can rely on the table as-is. Recommendation: rewrite §6.6 at the same depth using the code vocabulary.

### C2 - `session-delivery-queue` design is RFC-deep, but call-site adoption is shallower

The RFC spends protocol-level depth on cross-session enqueue and multi-target reporting (`docs/design/continue-work-signal-v2.md:430-465`). Code proves the generic storage payload shape (`src/infra/session-delivery-queue-storage.ts:67-96`, `src/infra/session-delivery-queue-storage.ts:254-313`) and post-compaction adoption (`src/auto-reply/reply/post-compaction-delegate-dispatch.ts:611-691`), but normal silent-wake still uses system events (`src/agents/subagent-announce.ts:1173-1198`). Recommendation: keep the substrate section deep, but add a "shipped call-site adoption matrix" that marks post-compaction as adopted and normal delegate returns as not yet migrated.

### C3 - Hedge timers are code-deep but RFC-shallow

The code has a dedicated hedge timer subsystem for unmatured TaskFlow delegates in quiet channels, with per-session idempotence, fresh chain-state reload at fire time, and natural-fire cleanup (`src/auto-reply/continuation/delegate-dispatch.ts:30-97`, `src/auto-reply/continuation/delegate-dispatch.ts:142-155`). The RFC only mentions the closed hedge-timer ref-leak failure in Appendix C/D (`docs/design/continue-work-signal-v2.md:1295`, `docs/design/continue-work-signal-v2.md:1347`). Recommendation: add a short §3.2 or §3.6 paragraph at runtime-mechanics depth.

### C4 - TaskFlow delegate store has more operational depth than §5.4 captures

The RFC says Task Flow provides persistence, cancellation, lifecycle tracking, observability, and session isolation (`docs/design/continue-work-signal-v2.md:757-773`). Code adds Zod state validation, corrupt-payload `failFlow`, `releasedAt` audit trail, FIFO ordering, matured vs unmatured filtering, and queue-depth breakdown (`src/auto-reply/continuation/delegate-store.ts:42-120`, `src/auto-reply/continuation/delegate-store.ts:194-239`, `src/auto-reply/continuation/delegate-store.ts:250-295`). Recommendation: expand §5.4 by one paragraph/table row for decode failure, maturity filtering, and queue-depth observability.

### C5 - Post-compaction delegate dispatch has more safety policy than the RFC lifecycle text

The RFC explains staged release and boot-file/context rehydration (`docs/design/continue-work-signal-v2.md:585-617`). Code also normalizes legacy flags, applies a 7-day TTL, enforces `maxDelegatesPerTurn` with bracket offsets, re-stages enqueue failures, and reports queued vs dropped counts (`src/auto-reply/reply/post-compaction-delegate-dispatch.ts:131-164`, `src/auto-reply/reply/post-compaction-delegate-dispatch.ts:536-697`). Recommendation: preserve current depth but add an "admission/drop/retry policy" subsection.

## Class D - Under-described in RFC

### D1 - Fallback delegate syntax supports delay and return-mode suffixes

RFC fallback syntax shows `[[CONTINUE_DELEGATE: <task>]]` and lists high-level limitations (`docs/design/continue-work-signal-v2.md:197-215`). Code parses `+Ns`, `| silent`, and `| silent-wake` suffixes (`src/auto-reply/tokens.ts:218-251`), and the prompt teaches these forms (`src/agents/system-prompt.ts:1018-1022`, `src/agents/system-prompt.ts:1108-1117`). Suggested insertion: §2.5, directly below limitations.

### D2 - Bracket signals take precedence over `continue_work()` tool requests in the same turn

The RFC says response syntax remains available as same-turn fallback (`docs/design/continue-work-signal-v2.md:230-238`) but does not state merge precedence. Code gives bracket syntax priority over tool-call requests (`src/auto-reply/continuation/signal.ts:47-49`, `src/auto-reply/continuation/signal.ts:118-131`). Suggested insertion: §2.6 or §3.4.

### D3 - `continue_delegate()` max-width rejection returns queue-depth diagnostics

RFC says width is bounded by `maxDelegatesPerTurn` (`docs/design/continue-work-signal-v2.md:674-681`, `docs/design/continue-work-signal-v2.md:966-975`). Code rejection returns `queuedDelegateDepth`, pending/runnable/scheduled counts, and staged post-compaction count (`src/agents/tools/continue-delegate-tool.ts:107-123`). Suggested insertion: §5.1 or §6.3.

### D4 - `request_compaction()` has an in-flight dedup guard and volatile guard state

RFC lists context floor and rate limit (`docs/design/continue-work-signal-v2.md:542-548`). Code also tracks `pendingCompactionSessions` to return `already_pending` for same-session duplicate requests (`src/agents/tools/request-compaction-tool.ts:47-53`, `src/agents/tools/request-compaction-tool.ts:147-154`) and documents module-level guard volatility (`src/agents/tools/request-compaction-tool.ts:30-37`). Suggested insertion: §4.3 guard table.

### D5 - Volitional compaction counter is TTL-bound diagnostic state

RFC describes `/status` `volitional: N` as count of agent-initiated compactions (`docs/design/continue-work-signal-v2.md:854-859`). Code stores it in a 24-hour expiring map and increments only on real compacted success (`src/agents/tools/request-compaction-tool.ts:27-28`, `src/agents/tools/request-compaction-tool.ts:219-232`, `src/agents/tools/request-compaction-tool.ts:280-291`). Suggested insertion: §6.3 field notes.

### D6 - System-event queue is intentionally in-memory, duplicate-suppressing, and traceparent-carrying

RFC leans on system events for continuation wake/enrichment (`docs/design/continue-work-signal-v2.md:291-297`, `docs/design/continue-work-signal-v2.md:589-595`). Code explicitly says the queue avoids persistence and is session-scoped (`src/infra/system-events.ts:1-3`), rejects empty/duplicate consecutive events, and stores optional validated `traceparent` (`src/infra/system-events.ts:119-140`). Suggested insertion: §3.1 or §6.6.

### D7 - Queue retry failure cleanup and soft-cap behavior is richer than the RFC line item

RFC names bounded backoff, cap 5, failed GC, and soft cap (`docs/design/continue-work-signal-v2.md:430-465`). Code details backoff `[5s, 25s, 120s, 600s]`, max retries 5, retry-budget-exhausted logs, failed-record prune, and queue-dir soft cap (`src/infra/session-delivery-queue-recovery.ts:66-68`, `src/infra/session-delivery-queue-recovery.ts:215-247`, `src/infra/session-delivery-queue-recovery.ts:257-339`, `src/infra/session-delivery-queue-storage.ts:13-16`, `src/infra/session-delivery-queue-storage.ts:276-284`). Suggested insertion: §3.6 retry/cleanup paragraph.

### D8 - Post-compaction delegate idempotency key inputs are concrete

RFC explains stable idempotency-key intent fields (`docs/design/continue-work-signal-v2.md:461`). Code builds the post-compaction delegate key from session key, compaction count, first-armed/created timestamp, sequence, and task hash (`src/infra/session-delivery-queue-storage.ts:126-168`). Suggested insertion: §3.6 idempotency-key collision domain.

### D9 - Chain-hop token accumulation waits briefly for child token data and may proceed with zero

RFC notes bracket-chain token accumulation is less reliable at announce boundary (`docs/design/continue-work-signal-v2.md:370-374`). Code implements a 150ms retry for child token data, logs if unavailable, then accumulates to parent chain cost when present (`src/agents/subagent-announce.ts:780-818`). Suggested insertion: §3.3 budget inheritance caveat.

## Class E - Over-described in RFC

### E1 - Exact §6.6 shipped span table is not implemented under those names

The RFC says the schema is shipped end-to-end (`docs/design/continue-work-signal-v2.md:921-929`) and lists span names at `docs/design/continue-work-signal-v2.md:931-949`. Code's canonical set differs (`src/infra/continuation-tracer.ts:215-224`) and source search found no implementation of the RFC table's exact names such as `continuation.delegate.enqueue`, `continuation.delegate.spawn`, `continuation.delegate.return`, `continuation.compaction.requested`, or `continuation.context_pressure.fire`. Recommendation: update RFC table to code, or mark the table as proposed and cite the shipped names separately.

### E2 - Response-token fallback telemetry via `continuation.delegate.enqueue via=response-token` is not the shipped path

RFC says response-token fallback emits a single `continuation.delegate.enqueue` span with `via=response-token` and no spawn span (`docs/design/continue-work-signal-v2.md:945-949`). Code emits `continuation.delegate.dispatch` for accepted bracket delegate dispatch and `continuation.delegate.fire` for timer callbacks (`src/auto-reply/reply/agent-runner.ts:2332-2353`, `src/auto-reply/reply/agent-runner.ts:2371-2395`, `src/infra/continuation-tracer.ts:446-477`, `src/infra/continuation-tracer.ts:602-645`). Recommendation: rewrite fallback telemetry subsection.

### E3 - Disabled-continuation metric claim is not visible in shipped code

RFC says disabled mode emits no spans and "`continuation.disabled` count metric ticks once per skipped enqueue attempt" (`docs/design/continue-work-signal-v2.md:945-949`). Code defines `continuation.disabled` as a span for cap/reservation rejects, not a metric (`src/infra/continuation-tracer.ts:480-549`), and disabled extraction logs then returns no signal (`src/auto-reply/continuation/signal.ts:64-71`). Recommendation: either add the metric or remove/clarify this as future telemetry.

### E4 - `targetSessionKey` descriptor-only rejection is not implemented

This is the schema-specific over-description paired with B1. RFC says a provided `targetSessionKey` is rejected as descriptor-only (`docs/design/continue-work-signal-v2.md:154-158`). Code cannot reject it intentionally because the tool schema does not expose/read it (`src/agents/tools/continue-delegate-tool.ts:17-39`, `src/agents/tools/continue-delegate-tool.ts:80-151`). Recommendation: remove current-runtime wording or implement explicit validation/rejection.

### E5 - "Injected into successor session" wording overstates post-compaction spawn certainty

RFC says post-compaction delegates are injected into the successor session and restore active working shape (`docs/design/continue-work-signal-v2.md:585-605`). Code first queues records and reports queued counts; spawn may occur later or fail/retry (`src/auto-reply/reply/post-compaction-delegate-dispatch.ts:283-314`, `src/auto-reply/reply/post-compaction-delegate-dispatch.ts:611-691`). Recommendation: make this "queued for delivery into the successor session" unless the code changes to await/confirm spawn before reporting release.
